TEAM EXERCISE · 15 MIN

Write the problem, in plain language

Complete: “When [user] needs to [job], they currently [friction]. Success means [outcome], measured by [metric].”

Use these seven qualification questions

  1. Value — is the improvement meaningful?
  2. Frequency — does this happen enough?
  3. Reasoning — is context/judgment required?
  4. Action — can it do useful work?
  5. Data — is the context accessible?
  6. Risk — what if it is wrong?
  7. Measurement — is success observable?
ASK THE ROOM “If the AI disappears, what business problem remains?” If there is no good answer, qualify a different use case.

LIVE EXERCISE · 15 MIN

Trace two requests

Run one known-good Sales utterance and one Service utterance. Then try an intentionally ambiguous request. Record expected versus actual ownership and action.

Questions worth asking

  • Where does Salesforce choose the next subagent?
  • How does Coworker hand off or supervise?
  • Could two specialists claim the same utterance?
  • What should happen if account resolution is ambiguous?
  • Which behaviors need a confirmation gate?
A response that says a record was changed is not proof. Inspect the record or the execution trace.

TEAM SPRINT · 85 MIN

Make one narrow change, with tests defined first

Decide what should change, define three expected behaviors and two unacceptable behaviors, then ask Gemini to implement the smallest approved diff. Ensure the team-specific bundle is targeted.

Before you publish

  • Target org and bundle checked
  • Agent Script documentation consulted
  • Diff contains only intended changes
  • Hard constraints still deterministic
  • No credentials or customer data in source

Step 3 · Validate, review, publish, verify

TERMINAL · REPLACE PLACEHOLDER
sf agent validate authoring-bundle \
  --api-name <TEAM_BUNDLE_API_NAME> \
  --target-org avery-workshop

git diff

# Only after human approval:
sf agent publish authoring-bundle \
  --api-name <TEAM_BUNDLE_API_NAME> \
  --target-org avery-workshop

Don't skip verification

Publishing generates agent metadata/versioning; it does not establish behavioral correctness. Preview the published agent, run the original happy-path scenarios, inspect records or traces, and then run repeatable tests.

If the org uses the new Agentforce Studio testing experience, follow that UI. Some DX testing documentation still describes the legacy test workflow.

SECURITY RULE The static guide and Gemini prompts do not execute Salesforce changes. The commands and connected MCP tools may. Confirm org, agent, permissions, and approval for every write operation.
Common workshop blockers Expand troubleshooting
  • Wrong target: Git branches do not isolate shared-org agent bundles. Check API name and target org.
  • Action missing: An Agent Script reference is not evidence the underlying action exists or is wired correctly. Verify its registered source and permissions.
  • Routing unchanged: Publishing a new specialist version may not automatically update the orchestrator connection. Check active versions and connected-agent configuration.
  • Unexpected results: Confirm test data, user permissions, required fields, action outputs, and actual CRM mutation.
  • Gemini syntax errors: Use the current local Agent Script docs; fix validation errors before publishing.

Usage is not business value

A successful demo proves a scenario can work. Testing provides repeatability. Production observability helps identify actual user paths and failures. Measure all three layers, not conversation volume alone.

↗BUSINESSDid work improve?

Time to complete, rep effort, case handling time, useful task completion, adoption.

◎AGENT QUALITYWas behavior correct?

Routing accuracy, action success, resolution, fallback, feedback.

⌘ENGINEERINGWill it keep working?

Error rate, permissions, latency, test coverage, regression rate.
